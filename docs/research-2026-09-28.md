TOPIC: nfc
----------------------------------------------------------------------------------------------------
SUMMARY: Lowest-friction free path on iPhone: a Shortcuts "NFC" personal automation set to Run Immediately (Ask Before Running off) that runs a small shortcut whose only action is Get Contents of URL doing an HTTPS POST with a JSON body {"item":"shower"} and an Authorization header. No app opens; at most a small "Running your automation" banner appears, and even that can be turned off with Notify When Run. It needs an iPhone XS/XR or newer (any iPhone with background tag reading; iPhone SE 2nd gen+ included) and works on every iOS since 13; NFC has always been one of the triggers Apple allows to run without confirmation. The trigger matches the tag's hardware UID and ignores NDEF content, so blank stickers work and a tag that also carries a URL record still fires the automation. Hard constraints from Apple's background-tag-reading rules: the screen must be on (phone "in use"), the phone must have been unlocked at least once since boot, and reading pauses while Camera, Wallet/Apple Pay, another NFC session or Airplane Mode is active. Whether a locked-but-awake phone runs the network action is disputed across guides (smart-home how-tos say no unlock needed; several 2025-26 guides say you get a notification and must authenticate), so plan on "raise phone (Face ID unlocks) then tap" and test. Writing a URL NDEF record instead relies on iOS background tag reading, which shows an "Open in Safari" banner that must be tapped (and asks to unlock if locked) - more friction, but it is the right fallback for Android/other phones. Buy plain NXP NTAG213 or NTAG215 PET stickers (~25 mm); 10-packs run roughly $5-10; NTAG213 (137 usable bytes) is plenty for a URL; get ferrite "on-metal" versions if sticking to metal. NFC Tools (free on iOS and Android) writes the URL record. On Android, tags are only read with the screen unlocked; http(s) URL tags open directly (Android 16 sends ACTION_VIEW, Android 17 adds an "open link" notification you must tap), and a background HTTP POST needs an automation app: Automate (free, 30-running-block cap) with "NFC tag scanned" + "HTTP request" blocks, Tasker (paid) with its built-in NFC Tag event + HTTP Request action, or NFC Tools Pro + NFC Tasks (the HTTP POST task is a Pro feature).

RECOMMENDATION: Use iOS Shortcuts NFC personal automations (Run Immediately, Notify When Run off or on as you prefer) that call one shared shortcut doing Get Contents of URL -> POST JSON with an Authorization: Bearer header to your HTTPS endpoint. Keep one shortcut ("Log routine item") holding the URL/token and pass the item name in via the automation's Run Shortcut input, so five stickers = five automations but one place to rotate the token. Buy a 10-pack of plain NXP NTAG213 or NTAG215 25 mm PET stickers (~$5-10) - NTAG213 is enough - and ferrite on-metal ones only where needed. Also write an https URL record (e.g. https://your.host/t/shower) to each tag with the free NFC Tools app: iOS ignores it for the automation, and it gives Android/guests a tap-to-open fallback; if you ever use an Android phone, build the same POST in Automate (free) with NFC tag scanned -> HTTP request. Expect the physical gesture to be "raise phone (Face ID unlocks), touch the top edge to the sticker for ~1 s"; make the endpoint idempotent (dedupe by item+day, timestamp server-side) because you may double-tap, and test once manually to answer the Always Allow prompt before relying on it in the morning.

HOW_TO: SERVER: expose POST https://your.host/api/routine that accepts JSON {"item":"shower"} with header Authorization: Bearer <TOKEN>, records item+server timestamp, and is idempotent per item per day. Return a tiny JSON like {"ok":true,"item":"shower"}.

TAGS: buy a 10-pack of NXP NTAG213 (or NTAG215) ~25 mm PET stickers (Tagstand NTAG213 10-pack $8.50; Amazon generics <$10). Stick one at each station (shower door frame, running shoes shelf, stretch mat, shoulder band hook, journal). On metal, use ferrite "on-metal" tags.

OPTIONAL URL RECORD (Android/guest fallback; iOS ignores it for the automation): NFC Tools (free, App Store) > Write > Add a record > URL/URI > https://your.host/t/shower > OK > Write > hold the TOP EDGE of the iPhone on the sticker when "Ready to Scan" appears. Repeat per tag.

SHORTCUT (do once, reused by every tag):
1. Shortcuts app > Shortcuts tab > + > rename to "Log routine item".
2. Add action "Get Contents of URL". URL: https://your.host/api/routine
3. Tap the action's "Show More" (chevron). Method: POST.
4. Headers: "+ Add new header" > Key: Authorization, Value: Bearer <TOKEN>. (Content-Type: application/json is added automatically for a JSON body; add it explicitly only if your server insists.)
5. Request Body: JSON > "Add new field" > Text > Key: item, Value: tap the value, choose the "Shortcut Input" variable (this is the item name passed in by each automation). For a quick test you can type shower literally.
6. (Optional feedback) add "Get Dictionary Value" (key ok) from Contents of URL, then "Show Notification" with "Logged <Shortcut Input>". Skip both for a silent run.
7. Run it once manually (tap the play button; it will ask for input - type shower). When Shortcuts asks "Allow 'Log routine item' to send ... to your.host?" choose Always Allow. Confirm the row appears on the server. Later, Details > Privacy on that shortcut shows/edits that grant.

AUTOMATION (one per sticker):
8. Shortcuts > Automation tab > + (New Automation) > scroll to "NFC" > Scan > hold the top edge of the iPhone against the sticker until it is recognized > name it "Shower tag" > Next.
9. Choose "Run Immediately" (this is Apple's "Ask Before Running = off"; tap "Don't Ask" if a confirmation appears) and set "Notify When Run" off for silence or on if you want the small banner as feedback. Next.
10. Actions: add "Run Shortcut" > pick "Log routine item" > tap "Show More"/input and set Input to the text shower. Done.
11. Repeat steps 8-10 for run, stretch, shoulders, journal, changing only the name and the input text. (Automations are per-device; redo them on a new iPhone.)

DAILY GESTURE: raise/tap to wake the phone (Face ID unlocks it), touch the top edge of the phone to the sticker for ~1 s. Nothing opens; the POST is sent in the background. Do not tap while Camera or Wallet is open or in Airplane Mode. Turn "Notify When Run" back on for a day if you want to confirm it fired.

ANDROID EQUIVALENT (Automate, free): New flow > "NFC tag scanned" block (match by tag ID; scan the tag once to capture it) > "HTTP request" block: Method POST, URL https://your.host/api/routine, Request headers {"Authorization":"Bearer <TOKEN>","Content-Type":"application/json"}, Request body "{\"item\":\"shower\"}" (as text) > optional "Toast show" > loop back to the NFC block. Start the flow, exclude Automate from battery optimization. Phone must be unlocked with screen on when you tap. Tasker alternative (paid): Profile > Event > Net > NFC Tag (by ID) > Task > Net > HTTP Request (POST, headers, body); disable the stock "Tags" app so Tasker gets the read.

VERIFY CORRECTIONS: Accurate current facts for the planner (as of 2026-09-28): (1) The iOS Shortcuts NFC trigger is unchanged through iOS 26/27 and keys strictly on the tag UID ('the contents of the NFC tag are ignored', Apple). Set the automation to Run Immediately; the per-automation 'Notify When Run' toggle can be switched off for NFC (it is only forced on for privacy-sensitive triggers like Location/Wi-Fi). (2) Hardware: iPhone XS/XR/SE 2nd gen and later read in the background; iPhone 7/8/X must open the Control Center NFC Tag Reader each time - not viable for tap-to-log. (3) Apple's only hard rules are the Core NFC background-reading conditions (phone in use/screen on, unlocked at least once since boot, not in Camera/Wallet/another NFC session/Airplane Mode). Whether the POST fires while the phone is locked-but-awake is unsettled; most 2025-26 guides say a locked phone shows a notification and waits for authentication, so design the gesture as 'raise to wake -> Face ID -> tap top edge' and test once. (4) Chip sizes: NTAG213 144 B user / 137 B NDEF, NTAG215 504 / 496, NTAG216 888 / 868; NTAG213 is enough for one URL. Tagstand NTAG213 10-pack $8.50, NFCW Shop 10-packs £4.96-£8.51, bulk NTAG215 ~$20/100. (5) Writing an https URL as the first record is fine on iPhone (iOS ignores it for the automation, and only shows the Safari banner separately) but on Android it changes dispatch: Android 16 sends it straight to the browser (ACTION_VIEW), Android 17 (stable since 16 June 2026) shows an 'open link' notification you must tap. Automate's NFC block expects a tag written by Automate (AAR first record) by default; 'Any' is unreliable for unwritten tags and a URL-first tag will be grabbed by the browser. So an Android user should dedicate tags to Automate (free, 30-running-block cap) rather than URL tags, or use NFC Tools Pro (paid) + NFC Tasks for HTTP POST, or Tasker ($4.49). Android reads tags only with the screen unlocked; the Pixel 'Require device unlock for NFC' toggle does not reliably enable locked reads. (6) Personal automations do not sync via iCloud - recreate the five NFC automations on any new iPhone. (7) Do not rely on a documented Get Contents of URL timeout or on a specific privacy prompt; keep the server endpoint idempotent per item per day and run the shortcut once manually before relying on it.

SUMMARY: Two free, automatic sources exist on the Mac and none on the iPhone itself. (1) knowledgeC.db (~/Library/Application Support/Knowledge/knowledgeC.db, stream '/app/usage', ZVALUESTRING = bundle id, ZSTARTDATE/ZENDDATE in Apple epoch + 978307200) still exists and is still parsed for app usage by tools tested on macOS 15 Sequoia and macOS 26 Tahoe, and a LaunchAgent using /usr/bin/python3 was reading it nightly through 2026-09-02; it holds ~30 days of second-resolution intervals for the LOCAL Mac only and requires Full Disk Access (on your Mac, macOS 26.6.2, even `ls` of that folder returns "Operation not permitted" from a non-FDA shell). (2) The Screen Time store on macOS is RMAdminStore-Local.sqlite under $(getconf DARWIN_USER_DIR)com.apple.ScreenTimeAgent/Store/ (the ~/Library/Application Support/com.apple.remotemanagementd/ path is the iOS location and does not exist on your Mac); its ZUSAGEBLOCK -> ZUSAGECATEGORY -> ZUSAGETIMEDITEM tables give per-app seconds per hourly block, with ZUSAGE.ZDEVICE -> ZCOREDEVICE.ZNAME naming the device and ZDEVICE IS NULL rows being the all-devices aggregate. With "Share Across Devices" on, iPhone usage syncs to the Mac: on older macOS it appeared as knowledgeC rows with non-NULL ZSOURCE.ZDEVICEID/ZMODEL; on Ventura/Sonoma/Sequoia-era tooling it lands in ~/Library/Biome/streams/restricted/App.InFocus/remote/<device_id>/ (SEGB protobuf) with device metadata in ~/Library/Biome/sync/sync.db, and in the hourly RMAdminStore blocks. Sync takes hours and Apple keeps only a couple of weeks. (3) Apple's Screen Time API (FamilyControls/ManagedSettings/DeviceActivity) is iOS/iPadOS-only, needs the privileged com.apple.developer.family-controls entitlement requested from Apple per app and per extension, and usage data is only renderable inside a DeviceActivityReport extension whose read-only sandbox blocks every output channel (network, app-group defaults, files, pasteboard, KVS), which Apple DTS confirmed in March 2026 is intentional; so no export to a web app. (4) ActivityWatch (free, open source, local-first, REST on localhost:5600, window titles + AFK) is a better Mac source than parsing Apple DBs but has no iOS client; its aw-import-screentime companion converts the Biome iPhone data into AW buckets. RescueTime's free Lite tier keeps 2 weeks of history and excludes the iOS app, so it does not help. (5) A LaunchAgent plist in ~/Library/LaunchAgents running /usr/bin/python3 hourly works if /usr/bin/python3 itself is added to Full Disk Access (TCC keys the grant to the exact executable path launchd runs); keep the API token in a chmod-600 file or the login Keychain, not in the 0644 plist. (6) Fallback: an iPhone Screen Time screenshot shows the daily total, one bar per hour with category-coloured segments, Most Used apps with h/m each, categories, pickups and notifications; there is no native export, so an LLM can only derive per-hour phone totals plus per-app daily totals from it.

RECOMMENDATION: Build the Mac side on knowledgeC.db first (second-resolution /app/usage intervals, bundle ids, ~30 days retention) with an hourly LaunchAgent running /usr/bin/python3 that has Full Disk Access, and treat RMAdminStore-Local.sqlite (under $(getconf DARWIN_USER_DIR)com.apple.ScreenTimeAgent/Store/) as the second query in the same script because it is the only Apple store that carries per-device hourly blocks for the iPhone once "Share Across Devices" is on (accept the multi-hour sync lag and roughly two-week retention). Do not plan around Apple's DeviceActivity API: it is iOS-only, needs an Apple-granted entitlement and a native app, and its report extension cannot send data anywhere. If you are willing to run one more agent, ActivityWatch is a strictly better Mac source (window titles, AFK detection, stable localhost REST API, no Full Disk Access needed) and its aw-import-screentime companion can pull the synced iPhone Biome data into the same API; RescueTime free is not worth it (2-week history, no iOS). Keep the iPhone screenshot-to-LLM path as the fallback for days when sync is late: it yields per-hour phone totals and per-app daily totals, which is enough to fill hourly "Phone" blocks with Unknown gaps.

HOW_TO: 1) Mac per-app intervals from knowledgeC.db (local Mac only; needs FDA). Safe read: copy the DB plus -wal/-shm to a temp dir, open the copy with `file:...?mode=ro` (do not use immutable=1 on the live file). Query:
SELECT ZOBJECT.ZVALUESTRING AS bundle, ZOBJECT.ZSTARTDATE+978307200 AS start_unix, ZOBJECT.ZENDDATE+978307200 AS end_unix, ZOBJECT.ZSECONDSFROMGMT AS tz_off, ZSOURCE.ZDEVICEID AS device_id, ZSOURCE.ZMODEL AS device_model FROM ZOBJECT LEFT JOIN ZSOURCE ON ZOBJECT.ZSOURCE=ZSOURCE.Z_PK LEFT JOIN ZSTRUCTUREDMETADATA ON ZOBJECT.ZSTRUCTUREDMETADATA=ZSTRUCTUREDMETADATA.Z_PK WHERE ZOBJECT.ZSTREAMNAME='/app/usage' AND ZOBJECT.ZENDDATE > strftime('%s','now','-26 hours')-978307200 ORDER BY start_unix;
Rows with device_id NULL are this Mac; non-NULL would be a synced device (legacy behaviour). Use '/app/inFocus' instead if you want strictly-frontmost intervals. Split each [start,end) across hour boundaries and sum seconds per (device, bundle, hour_start).

2) Hourly per-device blocks from the Screen Time store (includes iPhone after 'Share Across Devices' is on in Settings > Screen Time on the iPhone and System Settings > Screen Time on the Mac; sync lags hours):
DB="$(getconf DARWIN_USER_DIR)com.apple.ScreenTimeAgent/Store/RMAdminStore-Local.sqlite"
SELECT datetime(blk.ZSTARTDATE+978307200,'unixepoch','localtime') AS hour_start, dev.ZNAME AS device, COALESCE(ti.ZBUNDLEIDENTIFIER, ti.ZDOMAIN) AS item, ti.ZTOTALTIMEINSECONDS AS secs, blk.ZSCREENTIMEINSECONDS AS block_total FROM ZUSAGETIMEDITEM ti JOIN ZUSAGECATEGORY cat ON ti.ZCATEGORY=cat.Z_PK JOIN ZUSAGEBLOCK blk ON cat.ZBLOCK=blk.Z_PK JOIN ZUSAGE u ON blk.ZUSAGE=u.Z_PK LEFT JOIN ZCOREDEVICE dev ON u.ZDEVICE=dev.Z_PK WHERE u.ZDEVICE IS NOT NULL AND blk.ZSTARTDATE > strftime('%s','now','-26 hours')-978307200 ORDER BY blk.ZSTARTDATE, secs DESC;
(u.ZDEVICE IS NULL rows are the all-devices aggregate; exclude them to avoid double counting. block_total minus the sum of items = Unknown/system time for that hour.) If the iPhone rows are missing here, the alternative is decoding ~/Library/Biome/streams/restricted/App.InFocus/remote/<device_id>/ with aw-import-screentime (`aw-import-screentime devices` lists device UUIDs from ~/Library/Biome/sync/sync.db).

3) Script (~/bin/screentime_push.py, run by /usr/bin/python3, Apple's 3.9.6 is fine): import sqlite3, shutil, tempfile, json, urllib.request, time, os, pathlib; copy knowledgeC.db(+-wal,-shm) to tempfile.mkdtemp(); run query 1; bucket into {device,bundle,hour_start_utc,seconds}; also run query 2 directly against RMAdminStore (read-only URI) and emit {device,bundle,hour_start_local,seconds,block_total}; token = open(os.path.expanduser('~/.config/planner/token')).read().strip(); POST json.dumps({'source':'mac','generated_at':time.time(),'events':[...]}) with headers Content-Type: application/json and Authorization: Bearer <token> to os.environ['PLANNER_URL'] via urllib.request.urlopen(req, timeout=30); rmtree the temp dir; keep a ~/.config/planner/last_run watermark so you only send new hours. Server side: upsert on (device, bundle, hour_start) so re-sends are idempotent.

4) Secret: mkdir -p ~/.config/planner && (umask 077; printf '%s' 'YOUR_TOKEN' > ~/.config/planner/token); chmod 600 ~/.config/planner/token. Or keychain: `security add-generic-password -a planner -s planner-api -w` (prompts) and in the script subprocess `security find-generic-password -a planner -s planner-api -w`. Never put the token in the plist (plists must be 0644 and are readable by every local process).

5) LaunchAgent ~/Library/LaunchAgents/com.pranav.screentime-push.plist:

SUMMARY: As of late September 2026 the only option that is simultaneously free-forever, no-credit-card, never paused/sleeping, has a first-class scheduled job on the free plan, and lets a Shortcut or curl write a row with ONE HTTP call and ONE static bearer token is Cloudflare Workers (static assets for the PWA + a tiny JSON API in the same Worker) + D1 (SQLite) + a Cron Trigger. Supabase is excellent for the PWA side (PostgREST + RLS, pg_cron free) but free projects are still paused after 7 days of low activity and must be manually resumed in the dashboard, which silently breaks the NFC/Mac write path while you're away; it is also mid-migration from anon/service_role JWT keys to sb_publishable_/sb_secret_ keys (legacy keys removed by end of 2026). Firebase Spark never pauses and needs no card, but Cloud Functions/Scheduler are Blaze-only (no server-side daily rollup), and REST writes from a Shortcut need a Firebase ID token that expires hourly (so each tap = refresh call + write call) plus Firestore's verbose typed-value JSON. PocketBase has no viable free always-on host in 2026 (Fly trial only, Railway $1/mo credit, Render free has no persistent disk, Oracle Always Free needs a card and reclaims idle VMs). Turso and Neon are fine free databases but still need an API layer (Turso does have a bearer-token HTTP pipeline API). A purely local-first design (Dexie/IndexedDB + Dexie Cloud) is weaker for the NFC/Mac write path because iOS Safari has no Background Sync and the phone page must be open and online to receive writes; you still end up needing a server endpoint.

RECOMMENDATION: Use ONE Cloudflare Worker (free plan) that serves the PWA as static assets AND exposes a tiny JSON API, backed by D1 (SQLite), with a Cron Trigger for the daily rollup. Why this one: (1) free forever with no credit card and nothing ever pauses or sleeps (unlike Supabase's 7-day pause, Neon's scale-to-zero, Render/Fly/Railway sleeping or charging); (2) the free quotas dwarf a one-person planner: 100K Worker requests/day, D1 100K rows written/day and 5 M read/day, 5 GB, static asset requests unlimited and free; (3) scheduled job on the free plan (5 Cron Triggers/account) — Firebase Spark has no Functions/Scheduler at all, and Supabase's pg_cron is useless while the project is paused; (4) simplest possible auth for a single user: static bearer tokens stored as Worker secrets (`wrangler secret put`), no email/SMTP rate limits, no hourly-expiring ID tokens; (5) the Shortcut and the Mac script write a row with exactly ONE HTTP POST carrying one header; (6) D1 gives 7-day Time Travel restore free plus `wrangler d1 export` for backups. Auth model: three secrets — APP_TOKEN (typed once into the PWA's settings screen and kept in localStorage; never baked into the HTML/JS), SHORTCUT_TOKEN (pasted once into the Shortcut's header), MAC_TOKEN (kept in the macOS Keychain and read by the script). The Worker compares `Authorization: Bearer ...` against all three (constant-time compare), so any one can be rotated without touching the others. If you want a 'real login' instead of a token in the app, put Cloudflare Access (free ≤50 users, one-time-PIN to your email) in front of the site path and keep bearer tokens only for the /api/ingest route. Runner-up if you'd rather have Postgres + PostgREST out of the box: Supabase (RLS keyed on a custom header via current_setting('request.headers',true), pg_cron free) — but only if you accept keeping the project alive (a GitHub Actions heartbeat) and manually resuming it whenever it does pause, and you migrate to sb_publishable_/sb_secret_ keys now. Firebase Spark is a solid third (no pausing, no card) but the Shortcut needs two calls per tap (refresh ID token, then write), the Firestore typed JSON is awkward, and there is no free server-side scheduler. Skip PocketBase (no free always-on host in 2026) and skip pure local-first for the write path (iOS has no Background Sync; the page must be open to receive writes).

1) Setup (one-time, on the Mac):
   - Create a free Cloudflare account (email only). `npm create cloudflare@latest planner` (or `npx wrangler init`), choose a Worker with static assets.
   - `npx wrangler d1 create planner` → paste the binding into wrangler.jsonc:
     {"name":"planner","main":"src/worker.js",
      "assets":{"directory":"./public","binding":"ASSETS","not_found_handling":"single-page-application","run_worker_first":["/api/*"]},
      "d1_databases":[{"binding":"DB","database_name":"planner","database_id":"..."}],
      "triggers":{"crons":["5 8 * * *"]}}   // 08:05 UTC ≈ 04:05 EDT; cron is UTC
   - Schema (wrangler d1 execute planner --remote --file=schema.sql):
     events(id TEXT PRIMARY KEY, ts TEXT NOT NULL, kind TEXT NOT NULL, name TEXT, seconds INTEGER, grams REAL, kcal REAL, reps INTEGER, weight REAL, note TEXT, source TEXT, payload TEXT);
     meals(id TEXT PRIMARY KEY, name TEXT, kcal_per_100g REAL, protein_per_100g REAL, ...);   -- presaved meals
     day_summary(day TEXT PRIMARY KEY, sleep_s, work_s, study_s, screen_mac_s, screen_phone_s, unknown_s, json TEXT);

2) Worker (src/worker.js) sketch:
   export default {
     async fetch(req, env) {
       const url = new URL(req.url);
       if (!url.pathname.startsWith('/api/')) return env.ASSETS.fetch(req);
       const tok = (req.headers.get('Authorization')||'').replace(/^Bearer /,'');
       const role = tok===env.APP_TOKEN?'app':tok===env.SHORTCUT_TOKEN?'shortcut':tok===env.MAC_TOKEN?'mac':null;  // use a constant-time compare helper
       if (!role) return new Response('unauthorized',{status:401});
       if (url.pathname==='/api/events' && req.method==='POST') {
         const e = await req.json();
         await env.DB.prepare('INSERT OR IGNORE INTO events(id,ts,kind,name,seconds,grams,kcal,reps,weight,note,source,payload) VALUES(?,?,?,?,?,?,?,?,?,?,?,?)')
           .bind(e.id??crypto.randomUUID(), e.ts??new Date().toISOString(), e.kind, e.name??null, e.seconds??null, e.grams??null, e.kcal??null, e.reps??null, e.weight??null, e.note??null, role, JSON.stringify(e)).run();
         return Response.json({ok:true},{status:201});
       }
       if (role!=='app') return new Response('forbidden',{status:403});   // Shortcut/Mac tokens are write-only
       if (url.pathname==='/api/events' && req.method==='GET') { const {results}=await env.DB.prepare('SELECT * FROM events WHERE ts>=? AND ts<? ORDER BY ts').bind(url.searchParams.get('from'),url.searchParams.get('to')).all(); return Response.json(results); }
       // ...GET/PUT /api/meals, GET /api/day/:date etc.
       return new Response('not found',{status:404});
     },
     async scheduled(controller, env, ctx) {   // daily rollup
       const day = new Date(Date.now()-86400e3).toISOString().slice(0,10);
       const {results} = await env.DB.prepare("SELECT kind, name, SUM(COALESCE(seconds,0)) s FROM events WHERE substr(ts,1,10)=? GROUP BY kind,name").bind(day).all();
       const known = results.reduce((a,r)=>a+r.s,0);
       await env.DB.prepare('INSERT OR REPLACE INTO day_summary(day,unknown_s,json) VALUES(?,?,?)').bind(day, Math.max(0,86400-known), JSON.stringify(results)).run();
     }
   };

SUMMARY: Both free databases work directly from a browser/PWA. Open Food Facts (OFF) v2 product lookup is GET https://world.openfoodfacts.org/api/v2/product/{barcode}.json?fields=... and I verified today (2026-09-28) that it returns Access-Control-Allow-Origin: * (the widely repeated claim that OFF "does not support CORS" is wrong). Nutriment keys are exactly energy-kcal_100g, proteins_100g, carbohydrates_100g, fat_100g, fiber_100g, sugars_100g (plus _serving/_value/_unit variants), with serving_size (free text), serving_quantity (normalized grams) and nutrition_data_per ("100g" | "serving"). Rate limits are low: 15 product reads/min/IP and 10 searches/min/IP, a required User-Agent of the form AppName/Version (email), and a global limit that returns 503 (I hit one). v2 search is filter-only (no free text); full-text search is search-a-licious at search.openfoodfacts.org/search?q=..., but that host currently rejects cross-origin browser calls ("Disallowed CORS origin" even for an OFF origin), so free-text search needs a tiny proxy. USDA FoodData Central is public-domain, CORS-enabled (verified Access-Control-Allow-Origin: *), free key at fdc.nal.usda.gov/api-key-signup (1,000 req/hr; DEMO_KEY 30/hr and 50/day per IP), endpoints /fdc/v1/foods/search and /fdc/v1/food/{fdcId}; values are per 100 g with nutrient IDs 1008 kcal, 1003 protein, 1005 carbs, 1004 fat, 1079 fiber, 2000 total sugars (Branded; Foundation foods use 1063), and Branded foods carry gtinUpc, servingSize/servingSizeUnit, householdServingFullText and per-serving labelNutrients. Camera works in an installed iOS PWA but the permission is not persisted across launches. Data model: store every food per 100 g, compute grams×per100/100, keep the label's per-serving numbers plus serving grams, and be aware FDA rounding (21 CFR 101.9) makes per-serving→per-100 g conversion lossy; meals are recipes of (food, grams) logged with a scale factor. Do free-text search against USDA rather than OFF: OFF v2 search has no full-text mode and search-a-licious currently refuses cross-origin calls. Skip in-browser OCR: Tesseract.js is unreliable on nutrition panels; instead give the app a tiny authenticated POST /foods endpoint (or a CLI/JSON file import) and paste the label photo into Claude Code, which reads the label, computes per-100 g from serving grams, runs the 4/4/9 sanity check and calls the endpoint — that is the cheapest accurate path since the user already pays for Claude Code. For scanning, feature-detect window.BarcodeDetector but ship the `barcode-detector` ponyfill anyway (native is disabled on iOS), restrict formats to ['ean_13','upc_a','ean_8','upc_e'], require two consecutive identical decodes plus check-digit validation before lookup, and expect a camera permission prompt on each PWA launch on iOS.

HOW_TO: DATA MODEL (all per 100 g): Food { id, name, brand, source: 'off'|'usda'|'label', source_id (barcode or fdcId), per100: { kcal, protein_g, carb_g, fat_g, fiber_g, sugar_g }, serving_g (optional), label: { per_serving values, serving_text } (keep the raw label numbers for audit), density_note (ml vs g) }. LogEntry { ts, food_id | meal_id, grams (or meal scale), computed totals snapshot }. Meal (recipe) { id, name, items: [{ food_id, grams }], total_g = Σ grams, per100 = Σ(item.per100 × grams/100) / total_g × 100 }. Logging a meal at scale s (e.g. s = 0.5, or s = grams_eaten / total_g) records totals = meal_totals × s; snapshot the numbers at log time so later edits to a food don't rewrite history. Daily totals = Σ entries where local date matches; targets stored per day-of-week or as one set (kcal, protein_g, carb_g, fat_g).

MATH: nutrient = per100 × grams / 100. From a label given per serving of S grams: per100 = perServing × 100 / S. If the label only gives a household measure (e.g. '3/4 cup'), require the user to weigh one serving once and store S. Sanity check on any manual entry: |(4·protein + 4·carb + 9·fat) − kcal| ≤ ~15% of kcal (or ≤ 25 kcal at small servings) — flag, don't block, because fiber and rounding legitimately break the identity.

OFF LOOKUP (browser fetch, CORS ok): fetch(`https://world.openfoodfacts.org/api/v2/product/${code}.json?fields=code,product_name,brands,serving_size,serving_quantity,nutrition_data_per,nutriments,completeness,states_tags`) → if status===1 read product.nutriments['energy-kcal_100g'], proteins_100g, carbohydrates_100g, fat_100g, fiber_100g, sugars_100g (fall back to energy_100g/4.184 when energy-kcal_100g is absent). Map foodNutrients by nutrientId: 1008 kcal, 1003 protein, 1005 carb, 1004 fat, 1079 fiber, 2000 (or 1063) sugars; de-duplicate repeated nutrientIds (take the first). Values are already per 100 g. For Branded foods also store servingSize/servingSizeUnit and householdServingFullText. Handle 429 by backing off an hour (limits are per hour, rolling).

Expect a permission prompt each launch of the installed PWA on iOS; do not navigate (hash changes/reloads) mid-scan.

SUMMARY: An installed home-screen web app on iOS is a good fit for this planner as long as you design around four hard limits. (1) Storage: since iOS 17 a home-screen web app gets the same quota as Safari (origin quota up to ~60% of disk, LRU eviction only under pressure), the ITP 7-day script-storage purge is tied to Safari's days-of-use counter and home-screen web apps keep their own counter, and navigator.storage.persist() is auto-decided (no prompt) with "opened as a Home Screen web app" as a favourable heuristic, so IndexedDB is safe for daily-use data; still keep localStorage under 5 MiB and sync to a backend. (2) Notifications: Web Push works only in the installed app (iOS 16.4+), needs a user-gesture subscribe with userVisibleOnly + VAPID, and Safari revokes the subscription if pushes arrive without a visible notification (missing event.waitUntil is the classic cause); iOS 18.4+ adds Declarative Web Push (no service worker needed). There is no scheduled/local notification API on the web (Chrome's Notification Triggers was abandoned), so anything time-based must come from a server (a free Cloudflare Worker Cron Trigger sending VAPID pushes via Web Crypto/pushforge, or ntfy.sh) or from iOS itself (a Shortcuts Time-of-Day automation or Reminders), the latter being the most reliable bedtime nudge. (3) Launching/deep-linking: on iOS 18 a Shortcut "Open URL" (or any other app) opens the URL in Safari, not in the installed app; a webapp:// scheme worked in the iOS 26 beta but is reported broken by April 2026; so for NFC-sticker routines have the automation POST silently with "Get Contents of URL" (Run Immediately / Allow Running When Locked) and show the result the next time you open the app or via a push. Web NFC does not exist on iOS (Chrome for Android only), so Shortcuts NFC automations are the only iPhone path. (4) Background: JS/timers are frozen when the app is hidden or the screen locks; store absolute start timestamps, recompute on visibilitychange, and hold a Screen Wake Lock (works in home-screen web apps since iOS 18.4) while a rest/study timer is on screen. Camera works via getUserMedia since iOS 13.4 but has had repeated PWA-only regressions (iOS 18.0-18.1 fixed in 18.1.1; iOS 26-26.6 frames rotated 90°), so use <input type=file capture> for label photos. 2025-2026 changes: Safari 26 opens every Add-to-Home-Screen site as a web app (no manifest needed, "Open as Web App" toggle); EU removal was reversed before iOS 17.4 shipped; iOS 26.1 reportedly broke black-translucent status bars in installed web apps; Safari 26.2-26.6 added nothing web-app-specific beyond bug fixes.
